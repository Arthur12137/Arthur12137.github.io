实验一：网格世界里的导航与乱扔垃圾

Lab 1: Introduction to Agents

同一个智能体里有两件事：导航算法决定往哪走，策略决定什么时候扔垃圾。策略写得差，它会把自己家门堵死。

对应课件：lab1-initial.zip（Lab1.ipynb 与 5 个 .py 文件）

实验一把前两讲的概念落到一段能跑的 Python 上：一个 7×5 的网格世界，一个会用 BFS / DFS / A* 找路的智能体， 以及一个身上带着垃圾、要决定什么时候丢的「垃圾智能体」。代码量不大，但几乎每个设计都对应一个课上的概念：simulate() 是 sense → decide → act 循环，navigate() 是规划，litter_policy() 是策略，垃圾会留在地图上则是「非回合式环境」最直接的例子。

这份讲义按 notebook 的任务顺序走。所有数字（路径、展开数、第几趟堵死）都是在原版代码上跑出来的， 页面里的两个演示用 TypeScript 逐行复刻了 agent.py 和 litter_world.py， 并用测试核对过和 Python 输出完全一致。任务里的「Think about it」没有标准答案，这里给出的是一种有依据的回答。

代码是怎么分工的

一次模拟里，控制流是这样走的：

  1. simulate(world) 反复调用智能体和环境，直到到达目的地或者走满 100 步，最后调用 agent.reset()。
  2. agent.choose_action(world)：如果构造时传了 policy，就调用 policy(agent, world, target)； 否则直接调用 navigate()。策略决定做什么，导航决定往哪走。
  3. navigate() 读 world.blocked_cells()（这就是「感知」：它读的是整张图），去掉自己脚下那格， 然后决定要不要重新搜索。重新搜索的条件只有三个：目标或障碍集合变了（plan_key 变了）、缓存的路走完了、 缓存的下一格不和自己相邻。否则沿用上一次的计划。
  4. search() 按 search_algorithm 调用 bfs / dfs / astar，返回(path, expanded)：path 是从起点到终点的格子列表，找不到时是 None；expanded 是按顺序展开过的格子。
  5. world.step({id: action}) 检查动作是否合法：目标格在图内、可通行、和当前位置相邻、（垃圾世界里）身上不到 6 件。 合法就移动并返回 'moved'，不合法就原地不动返回 'wait'。

第 3 步的缓存值得注意：智能体保存着 path 和 plan_key，只要世界没变就一直按原计划走。 这是一份关于「接下来怎么走」的内部状态，也是一种很弱的「承诺」，Task 1.4 会用到。

Task 1.2 · Compare BFS, DFS and A*

Task 1.2：三种搜索，同一张图

三个算法共用同一个骨架：从 frontier 里取一个格子「展开」，是终点就停，否则把它的邻居放进 frontier。区别只在 frontier 是什么：

广度优先
BFS (deque)
frontier 是队列，先进先出，所以按离起点的步数一层一层展开。邻居被放进队列的那一刻写下 parent。 每一步代价都是 1 时，BFS 找到的一定是最短路。代价：要把终点之前所有更近的格子都展开一遍。
ENExpands the earliest discovered cell first; with unit costs it returns a shortest path.
深度优先
DFS (list as stack)
frontier 是栈，后进先出，总是先展开最新放进去的格子。邻居顺序是 LEFT, RIGHT, UP, DOWN， DOWN 最后入栈、最先出栈，所以它先一路往下钻。它从不比较路径长短，返回的路不保证最短。 和 BFS 一样，parent 在入栈时就写下，之后不再改。
ENExpands the most recently discovered cell first; the path it returns need not be shortest.
A* 搜索
A* (heap)
frontier 是按 f=g+h 排序的最小堆：g 是从起点走到这里的步数，h 是到终点的曼哈顿距离。 堆里放的是 (f, 序号, g, 格子)，f 相同时按序号，也就是先放进去的先出来。 一个格子如果后来找到更短的 g，会被再放一次，旧的那条在弹出时因为 cost != best[current] 被跳过。
ENExpands the cell with the smallest g + h, where h is the Manhattan distance to the goal.
g(n)
从起点到格子 n 已经走了几步（代码里的 cost / best[n]）
h(n)
曼哈顿距离：在只能上下左右走、每步代价 1 的网格上，它从不高估真实距离，所以 A* 返回的仍是最短路
f(n)
经过 n 的路径总长的估计，也是堆里的 priority

Task 1.2 · 为什么 DFS 绕远

DFS 为什么走了 17 步

从 (0,2) 出发，跟着栈走前几步：

  1. 展开 (0,2)：邻居按 LEFT（出界）、RIGHT (1,2)、UP (0,1)、DOWN (0,3) 入栈，三个都记 parent = (0,2)。栈顶是 (0,3)。
  2. 展开 (0,3)：入栈 (1,3)、(0,4)。栈顶 (0,4)，于是一直往下钻到底边。
  3. 展开 (0,4)：只剩 RIGHT (1,4) 没被记过，入栈。展开 (1,4)：它的 UP (1,3) 早在第 2 步就被记了 parent，不会再入栈，只剩 (2,4)。
  4. 这样一路下去，第 1、3、5 列的格子在左边一列展开时就被「预订」了，搜索只能沿着第 0、2、4、6 列上下蛇行： 下到底、右移、上到顶、右移……直到在 (6,4) 发现 (6,3)。

结果是展开的 18 个格子恰好就是路径上的 18 个格子：DFS 这一次一个岔路都没试，一条道走到了终点，只是这条道很长。 所以路径绕远的根本原因是深度优先的顺序本身：它总是顺着最新的分支往下走，从不比较哪条路更短。 「入栈时记 parent」决定的是具体绕了哪一条弯路。下面把另一种常见写法（出栈时才确认访问）放在一起对比，在这张图上它绕得更远：

出栈时才确认访问的版本几乎把 35 个格子全走了一遍（31 步）。两种都是 DFS，都不保证最短；想要最短路就用 BFS 或 A*。

Task 1.3 · What Kind of Environment Is This?

Task 1.3：这是什么样的环境

维度Task 1 的导航环境依据（代码里的哪一处）
可达可达navigate() 每一步都调用 world.blocked_cells()，整张图的通行情况都拿得到，而且是最新的。
确定确定同一状态下同一个合法动作结果唯一；不合法的动作一定原地不动。代码里没有任何随机失败。
静态静态只有一个智能体，空世界里除了它的移动没有任何东西在变。
回合式以「一步」为单位是非回合式这一步走到哪决定下一步能去哪。以「一趟」为单位，空世界每趟 reset 回家、互不影响；垃圾世界里连「趟」之间也互相影响（Task 2.3）。

README 追问：如果条件变了呢？

  • 障碍会移动：变成动态；缓存的计划会过时，而 navigate() 只有在 blocked 集合变了才重新规划，所以这套代码还能应付。
  • 只能看到相邻格子：变成不可达（部分可观测）；blocked_cells() 这种「读整张图」的写法就不再合法，智能体需要自己记地图，也就是变成基于模型的。
  • 几个智能体同时移动：变成动态、多智能体；彼此会抢格子。注意现有的 LitterWorld.step() 在多个智能体时有问题（见文末的坑）。
  • 动作有时失败：变成不确定；智能体要检查动作结果，发现和预期不同就重新规划。

第 2 讲讲义最后一个演示（环境性质）就是把这四个条件逐个打开，统计同一个智能体的重新规划次数和步数。

Task 1.4 · What Kind of Agent Is It?

Task 1.4：导航智能体属于哪一类

描述符合吗理由
Reactive不完全它先搜索出一整条路再照着走，并没有按当前状态查表出动作。每一步重新读 blocked_cells() 这一点带有反应性。
Model-based部分它用到环境结构的模型（网格尺寸、邻接关系、障碍集合）来规划，还保存着 path 和 plan_key 作为内部状态。但这个模型是每步从世界直接读来的，不是自己从观测里建起来的。
Goal-based符合end_position 是显式的目标，search() 规划出到达目标的动作序列。这是最贴切的描述。
Utility-based不符合没有显式的效用函数。BFS / A* 返回最短路，可以说隐含地用「步数」给路线排了序；DFS 连这一点都没有。
BDI不符合代码里没有显式的信念、愿望、意图三样表示。缓存的 path 像一个被承诺的计划，但 README 提醒：有目标不等于 BDI。

Task 2.3 · What Happens Over Time?

Task 2.3：时间长了会怎样

按 README 的五个问题，用演示里的结果回答：

  1. 垃圾反复丢在哪？家门口：(1,2)、(0,1)、(0,3)。基本策略总在第一次移动之后丢，而第一次移动永远从房子出发。
  2. 有格子被堵吗？有。每趟丢 2 件，同一格两趟就到 4 件。BFS 下是 (1,2) → (0,1) → (0,3) 的顺序，DFS 下是 (0,3) → (0,1) → (1,2)， 因为被堵的格子会让下一趟的路线改走另一个门。
  3. 堵住的格子会影响后面的路线吗？会。BFS 下第 6 趟去 (1,0) 时 (1,2) 和 (0,1) 都已堵死，只能从 (0,3) 出门绕一大圈， 移动次数从前几趟的 3 次变成 7 次；第 7 趟三个门全堵，搜索返回 None，智能体原地 wait 满 100 步。 之后 reset 每次加 2 件：4 件、6 件，到 6 件时就算门开着也走不动了。
  4. 一趟里的动作会影响后面的趟吗？会，这正是症结：地上的垃圾在 reset() 之后仍然留着。
  5. 所以这个任务是回合式还是非回合式？非回合式。前一趟的 drop 改变了后一趟面对的世界。

Tasks 2.4–2.5 · Design a Better Policy

Task 2.4：设计一个更好的策略

README 给了五个设计问题，每个问题都指向一个可以放进策略的条件：

  1. 是否总要立刻丢？不必。推迟到一个合适的格子再丢。
  2. 丢之前要不要检查当前格？要。房子上 drop 会被环境拒绝；公园上丢到 4 件，目的地本身就不可达了。
  3. 格子里已有的垃圾要不要考虑？要。当前件数 + 身上件数 决定了丢完之后这一格会不会被堵。
  4. 有些格子是不是更适合丢？是。堵住一个死角无所谓，堵住某个房子唯一的出口就是灾难。
  5. 到达目的地会不会影响决定？到了公园 simulate 就结束了，在公园上根本来不及丢；这也意味着必须在路上找地方丢。

一个直观的改法是「只在丢完仍可通行的格子丢」（演示里的第三种策略）。它从不堵任何格子，但在 BFS 下第 5 趟就失败，比基本策略还早： BFS 去 (1,0) 只经过 (1,2)、(1,1) 两个中间格，每格丢过一次 2 件之后，再丢就会到 4 件，于是它一件也不丢，身上的垃圾涨到 6 件。 这个世界里没有垃圾桶，垃圾只增不减，「不堵格子」和「不背垃圾」不能同时做到。

所以要允许堵格子，但要挑格子。下面这个参考策略的规则是：身上有垃圾、脚下不是房子也不是公园，并且满足下面两条之一就丢—— 丢完这一格仍可通行；或者这一格被堵之后，每个房子仍然能走到每个公园。第二条用 BFS 检查连通性，这是用到了对世界的模型： 在真正动手之前，先预测这个动作会造成什么。

这段代码放进 notebook 原样运行过（DFS，连跑 12 趟全部到达）。

Task 2.5 的比较（60 趟，random.seed(0) 的目的地序列）：基本策略第 7 趟失败；参考策略在 BFS 下第 41 趟、DFS 下第 33 趟才第一次失败， 期间所有趟都到达，而且没有一个房子被围死。它失败的方式也不同：门始终没被堵，失败是因为路线上所有格子要么已经 2 件、要么一堵就会切断别人的路， 连续两趟找不到能丢的地方，身上涨到 6 件。

任何策略最终都会失败，而且可以算出一个上界：不论策略怎么写，最迟第几趟一定出不了门。 思路是数垃圾：垃圾只增不减，地上能放的有限，放不下的只能背在身上。

策略能决定的是失败来得多晚、以什么方式失败。这正是非回合式环境的特点：每一趟的后果都在累积。

Tasks 2.2, 2.6 · Has the Type of Agent Changed?

Task 2.2 与 2.6：智能体的类型变了吗

Task 2.2，基本策略。它的形式是「条件满足 → 执行动作」的规则，看起来是反应式的。但条件里的 did_drop和 moves_taken 是智能体自己记的内部状态，当前观测里看不出「这一趟丢过没有」。所以它比纯粹的at​=π(ot​) 多了两位记忆。它也不是目标导向的：丢垃圾不为任何目标服务。

Task 2.6，参考改进策略下的垃圾智能体：

Reactive是每一步都对当前格子的状态（件数、是否是房子或公园）直接作出反应。
Model-based是它读 world.trash 的累计件数，还用网格模型预测「堵住这一格之后还连不连通」。
Goal-based是到达目的地是显式目标；「不切断房子到公园的路」是它在选择 drop 时维护的约束。
BDI否代码里没有显式的信念、愿望、意图结构，也没有承诺与重新考虑的机制。

和 Task 1 的导航智能体比，多出来的是「对自己动作后果的预测」：这让它更接近第 2 讲说的基于模型、目标导向的智能体。

复习提醒

代码里容易看错的地方

  1. 1
    notebook 第 2 格的 BLOCK_THRESHOLD = 2 不起作用
    LitterWorld.is_passable() 用的是 litter_world.py 模块里的 BLOCK_THRESHOLD = 4。改 notebook 里的变量，世界的规则不会变。更隐蔽的是：如果你在 notebook 里写的策略直接引用 BLOCK_THRESHOLD，拿到的是 2。例如「当前件数 + 身上件数 < BLOCK_THRESHOLD」在身上带 2 件时永远不成立，智能体一件也不丢，第 3 趟走不动。要用 litter_world.BLOCK_THRESHOLD。同一格里的 LITTER_PER_AGENT、NUM_EPISODES、POPULATION 也都没有被世界用到。
  2. 2
    在房子上 drop 时，LitterWorld.step() 返回的是字符串
    正常情况下 step() 返回「智能体编号 → 反馈」的字典；在房子上 drop 返回 'cannot litter at a house'，身上没垃圾时返回 'nothing to drop'。如果你写 feedback[agent.unique_id]，会得到字符串下标错误。多智能体时，这个提前 return 还会让同一拍里其他智能体都不动。
  3. 3
    公园也能被丢垃圾
    add_trash() 只排除房子。公园被丢到 4 件后，valid_endpoints() 返回 False，搜索返回 None，navigate() 一直给出 wait，智能体原地待满 100 步。策略里要排除公园。
  4. 4
    reset() 会随机挑一个公园
    Agent.reset() / Litter_Agent.reset() 里有 random.choice(PARK_POSITIONS)。notebook 在下一趟开始前又覆盖了 end_position，但 reset 仍然消耗了一个随机数。不设种子的话每次运行的目的地序列都不同，所以你的「第几趟堵死」可能和讲义不一样；规律（6 趟左右把三个门口填满）不变。
  5. 5
    drop 那一步也会在 trail 里记一个位置
    simulate() 每一步都 append 当前位置。drop 不移动，所以 trail 里会出现连续两个相同的格子。len(trail) − 1 是「步数」而不是「移动次数」：BFS 去 (1,0) 移动 3 次，加一次 drop，trail 长度减一是 4。
  6. 6
    notebook 最后一格没有把 better_policy 传进去
    那一格创建 Litter_Agent 时没有 policy= 参数，跑的是纯 navigate()，也就是「从不丢」：第 3 趟身上 6 件、走不动。另外 better_policy 的占位代码是一个空 return，返回 None 会被当成 wait：直接传进去而不实现，智能体一步都不会动。
  7. 7
    多智能体时 LitterWorld.step() 的计数有问题
    它在每个智能体的循环里都调用一次 EmptyWorld.step()，而后者会移动所有智能体。第一次调用时大家都移动了；第二次调用时目标格就是当前格，判为 wait。结果第二个智能体明明走了，它的 moves_taken 却不会增加，基本策略对它永远不触发。实验只用一个智能体，所以不影响结果。
  8. 8
    坐标是 (列, 行)，y 向下增大
    (4,0) 在第一行、第五列；UP 是 (0, −1)。和数学里的直角坐标方向相反，手推路径时最容易在这里出错。
  9. 9
    DFS 展开少不等于找得快
    (0,2)→(6,3) 时 DFS 只展开 18 个格子（比 BFS 的 31 少），但路径长 17 步（BFS 7 步）。展开数衡量的是规划时的计算，路径长衡量的是执行时要走的步数。

这一讲要带走的一句话

导航算法只管从这里到那里，策略决定这一步做什么；在一个会累积后果的环境里，策略要预测自己的动作会让以后的世界变成什么样。

The navigation algorithm only gets the agent from here to there; the policy decides what to do at each step, and in an environment where consequences accumulate it has to predict what its actions will do to the world it will face later.
